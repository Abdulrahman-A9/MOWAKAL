# تقرير توسعة واجهة MOWAKAL

## 1. الملخص

تمت توسعة واجهة MOWAKAL من دليل محامين ولوحات مختصرة إلى منصة خدمات قانونية عربية متكاملة بصريًا للأدوار الثلاثة: العميل، المحامي، ومدير المنصة. ما يزال التنفيذ Frontend فقط باستخدام HTML وCSS وVanilla JavaScript وبيانات محاكاة.

## 2. ما تمت إضافته

- طبقة بيانات موحدة بكيانات مستقرة ومعرفات واضحة.
- نظام حالات مشترك للطلبات والاستشارات والقضايا والمدفوعات والتوثيق.
- قائمة تنقل موحدة ومتجاوبة للأدوار الثلاثة.
- هيدر عام فعلي للصفحة الرئيسية ودليل المحامين وملفات المحامين، مع تنقل متجاوب وأزرار الدخول وإنشاء الحساب.
- قسم تخصصات قانونية في الصفحة الرئيسية يربط مباشرة بدليل المحامين بحسب المجال.
- توحيد إدارة مستخدمي المنصة في صفحة واحدة للأدمن مع تبويبات وفلاتر للعملاء والمحامين ومديري المنصة والبحث حسب البيانات والحالة.
- ربط بطاقات تخصصات الصفحة الرئيسية بصفحة عامة مستقلة لطلب الخدمة، بمراحل متعددة ومن دون لوحة العميل أو سايدبارها.
- رحلة إنشاء طلب خدمة متعددة الخطوات.
- تطوير صفحة الملف المهني للمحامي بنموذج متكامل للمعلومات المهنية والنبذة ومجالات الخدمة، مع معاينة مباشرة للملف ورابط لعرضه للعميل.
- ربط ما يحفظه المحامي بملفه العام وبطاقات الدليل، مع حفظ محلي في المتصفح عبر LocalStorage.
- تفاصيل الطلب مع مسار زمني وتفاصيل المستندات والطرف المرتبط.
- صفحات القضايا والاستشارات والمواعيد والمستندات والرسائل والمدفوعات والتقييمات والملفات الشخصية.
- مساحة إدارة تشمل المستخدمين والعملاء والمحامين والتوثيق والخدمات والطلبات والقضايا والمدفوعات وسجل الأنشطة والتقارير والإعدادات.
- تقليل نطاق لوحة الإدارة العامة إلى بيانات حساب أساسية وخدمات وتقارير إجمالية وسجل تدقيق مختصر، وإخراج تفاصيل الطلبات والقضايا والمراسلات والمستندات والمدفوعات والتقييمات من مساحتها.
- فصل بيانات العرض الخاصة بالإدارة في `admin-data.js` ببيانات تشغيلية محدودة، بدل تحميل مجموعة بيانات المحاكاة الكاملة داخل صفحات الإدارة.
- خريطة ربط مستقبلية للباكند وملف كيانات الواجهة.

## 4. رحلة العميل

الرئيسية ← الخدمات القانونية ← طلب خدمة ← تفاصيل الطلب والمستندات ← اختيار المحامي والموعد ← إرسال الطلب ← متابعة الحالة ← الاستشارة أو القضية ← المستندات والرسائل ← الدفع ← الإغلاق والتقييم.

## 5. رحلة المحامي

لوحة المحامي ← الطلبات الجديدة ← فتح تفاصيل الطلب ← قبول أو رفض أو طلب معلومات إضافية ← الاستشارات والمواعيد ← القضايا والمستندات ← التواصل مع العميل ← الفواتير والتقييمات.

## 6. رحلة مدير المنصة

لوحة الإدارة ← مراجعة توثيق المحامين ← إدارة الخدمات ← متابعة الطلبات والاستشارات والقضايا ← مراجعة البيانات الوصفية للمستندات والمدفوعات ← التقييمات ← سجل الأنشطة ← التقارير والإعدادات.

## 8. معمارية JavaScript

- mock-data.js: مصدر محاكاة مركزي للكيانات والعلاقات والحالات.
- ui.js: أدوات مشتركة للتنبيهات، الشارات، النوافذ، التحقق من النصوص، والتقييمات.
- navigation.js: بناء القوائم الجانبية والتنقل المتجاوب حسب الدور.
- platform.js: منطق الصفحات، العرض، البحث، الفلاتر، النماذج، الحالات، والعمليات المحاكاة.
- main.js: نقطة تشغيل مشتركة للصفحات العامة وصفحات المنصة الحالية.

## 9. هيكل بيانات المحاكاة

تستخدم البيانات معرفات مثل REQ-1001 وCASE-2001 وLAW-001، وتربط الطلب بالعميل والمحامي والخدمة والمستند والموعد والفاتورة. هذا يسمح باستبدال مصدر المحاكاة بطلبات API مستقبلية دون تغيير نموذج العرض بالكامل.

## 10. الجاهزية للـ API

تم توثيق نقاط الربط المتوقعة في docs/frontend-backend-map.md. لا تتصل الواجهة مباشرة بـ MySQL، ولا تحتوي على مصادقة حقيقية أو صلاحيات موثوقة أو تخزين ملفات حقيقي.

## 11. السلوك المتجاوب

- القائمة الجانبية تتحول إلى قائمة جوال قابلة للفتح والإغلاق.
- البطاقات والشبكات تتحول إلى عمود واحد على الشاشات الصغيرة.
- الجداول تتحول إلى تمرير أفقي نظيف.
- النماذج متعددة الحقول تتكدس عموديًا.
- الرسائل والمواعيد والتفاصيل تعمل على الشاشات الصغيرة.
- تم الحفاظ على lang=ar و dir=rtl في الصفحات الجديدة.

## 12. الاختبارات المنفذة

- فحص صياغة جميع ملفات JavaScript باستخدام Node.js: ناجح.
- فحص الروابط والملفات المحلية لجميع صفحات HTML: ناجح.
- اختبار متصفح Playwright لـ ٥٠ صفحة: جميع الاستجابات HTTP 200 ولا توجد أخطاء Console أو Page Error.
- اختبار البحث في الخدمات: انخفضت النتائج من ١٠ إلى ٢ عند البحث عن «العقود».
- اختبار معالج إنشاء الطلب متعدد الخطوات، ملخص الطلب، وإشعار الإرسال: ناجح.
- اختبار قبول طلب توثيق محامٍ وتحديث الحالة: ناجح.
- اختبار حالة معرّف طلب غير صحيح: تظهر حالة عدم العثور بدل كسر الصفحة.
- اختبار القائمة الجانبية على الجوال فتحًا وإغلاقًا: ناجح.
- اختبار الاستجابة على سطح المكتب 1440px، واللوحي 768px، والجوال 375px لأربع صفحات ممثلة: دون overflow أفقي أو جذور صفحات فارغة.
- مراجعة بصرية بلقطات سطح المكتب والجوال للوحة العميل: ناجحة.
- فحص الصفحة الرئيسية: الهيدر، التنقل، قسم التخصصات، بطاقات المحامين، والقائمة الجوالة: ناجح.
- اختبار إدارة المستخدمين: عرض الكل، فلتر العملاء، فلتر المحامين، فلتر مديري المنصة، والبحث/الحالة: ناجح.
- اختبار الانتقال من بطاقات التخصصات إلى صفحة الطلب العامة، وتحديد الخدمة مسبقًا، وإكمال المراحل الخمس وعرض الملخص دون الانتقال إلى لوحة العميل: ناجح.
- اختبار صفحة الطلب العامة على الجوال: لا يوجد overflow أفقي، والهيدر العام ظاهر.
- اختبار نموذج الملف المهني للمحامي: معاينة مباشرة، والتحقق من إلزام مجالات الخدمة، وحفظ جميع الحقول بنجاح.
- اختبار ظهور الاسم والتخصص والترخيص والخبرة والمدينة والأتعاب والمواعيد والنبذة ومجالات الخدمة في الملف العام ودليل المحامين بعد التنقل وإعادة التحميل: ناجح.
- اختبار الملف المهني وصفحة المحامي العامة عند عرض 375px، دون تمرير أفقي أو أخطاء في المتصفح: ناجح.
- تحسين shell لوحات التحكم: إضافة هيدر موحّد لمساحات العميل والمحامي والإدارة يتضمن مسار الصفحة والبحث والإشعارات وبيانات المستخدم.
- إعادة تنظيم السايدبار إلى مجموعات وظيفية بعناوين وفواصل واضحة مع تثبيت منطقة المستخدم وتمرير داخلي عند الحاجة.
- فحص آلي مباشر لوجود الهيدر، ترتيب العنوان قبل الإحصائيات، عدد مجموعات السايدبار، والرابط النشط في لوحات الأدوار الثلاثة: ناجح.

هذه الاختبارات تخص الواجهة المحاكاة فقط ولا تثبت وجود Backend أو API أو MySQL.

## 13. الحدود المعروفة

- لا يوجد Backend أو MySQL أو مصادقة حقيقية.
- تقليل البيانات في لوحة الإدارة تحسين لواجهة المحاكاة فقط، وليس حماية وصول؛ صفحات الموقع وملفات JavaScript عامة، لذلك يمنع وضع بيانات حقيقية قبل بناء مصادقة وRBAC وواجهات API معزولة على الخادم.
- التغييرات على الحالات والرسائل والنماذج داخل الذاكرة فقط.
- تعديلات الملف المهني تحفظ محليًا في المتصفح ذاته؛ مزامنتها بين المستخدمين والأجهزة تتطلب API وقاعدة بيانات.
- اختيار الملفات يسجل أسماء الملفات ولا يرفع محتواها.
- المدفوعات والفواتير محاكاة عرضية فقط.
- لا توجد WebSockets أو مكالمات مرئية فعلية أو إشعارات حقيقية.
- يجب تطبيق الصلاحيات والخصوصية والتحقق من الملكية في الباكند.

## 14. الخطوات المقترحة للباكند

1. اعتماد نموذج الكيانات والحالات وتثبيت عقود API.
2. بناء المصادقة والأدوار والصلاحيات والتحقق من ملكية الموارد.
3. إنشاء جداول المستخدمين والمحامين والخدمات والطلبات والقضايا والمواعيد والمستندات والمدفوعات.
4. استبدال طبقة المحاكاة بطبقة API مع حالات تحميل وأخطاء حقيقية.
5. إضافة تخزين ملفات آمن وسجل تدقيق وصلاحيات دقيقة للمستندات.
6. ربط مزود الدفع والإشعارات والمراسلة بعد اعتماد المتطلبات التشغيلية.
